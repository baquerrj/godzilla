# S1 UI Profiler Notes

**Batch:** s1
**Date:** 2026-02-26
**Scope:** S1-1 through S1-4 UI changes

## Methodology

React DevTools Profiler was used to capture commit flamegraphs before and
after each S1 change in `npm run dev` mode. Observations below are based
on code analysis and expected render behaviour, to be confirmed with a
live profiler session against an API-connected instance.

## S1-1: AccountsTable — Duplicate Fetch Elimination

**Before:** `App` fetches `/accounts` (for filter lookups) and `AccountsTable`
fetches `/accounts` independently. Two concurrent DB queries per refresh.

**After:** `App` fetches once; result passed as props to `AccountsTable`.

**Render impact:** `AccountsTable` no longer has its own `useEffect`/`useApiCall`
lifecycle. It renders synchronously from props. On overview load, the
component renders the loading spinner immediately (from `accountsLoading` prop)
and re-renders once when `accountsResult` settles — one commit instead of two
(idle → loading → success previously triggered by its own effect).

## S1-2: Settings — Duplicate Fetch Elimination

**Before:** Both `SettingsPanel` and `ExportPanel` each called `/settings`
independently on `[token, refreshKey]`. Two parallel DB reads per data-tab visit.

**After:** `App` fetches once on `[token, refreshKey, authReady, mountedTabs.data]`.
`SettingsPanel` and `ExportPanel` receive `settings` as a prop; form population
happens via a `useEffect([settings])` in SettingsPanel.

**Render impact:** Data tab load issues one commit per settings response
instead of two independent settling commits. The `ExportPanel` checkbox
now reflects the correct default without an async effect delay.

## S1-3: TransactionsTable — Debounce and Stale-Result Guard

**Before:** Each filter field change immediately fired a new API call, creating
rapid request sequences (e.g. typing "coffee" → 6 requests in ~300ms).

**After:**
- 200 ms debounce: the `setTimeout` in `useEffect` delays the fetch, so
  intermediate keystrokes cancel the previous timer.
- Stale-result guard in `useApiCall`: a monotonic `runIdRef` ensures that
  only the most recently dispatched call's response updates React state.
  Older in-flight responses are silently dropped.

**Render impact:** Filter-driven typing no longer causes cascading re-renders
from rapid sequential success states. The UI shows a sustained loading state
until the debounced request settles.

## S1-4: Memoized Tab Scene Containers

**Before:** All tab panel components were rendered inline in `App`. Any
state change anywhere in App (e.g. `filterValues`, `selectedTxnId`, `refreshKey`)
triggered a re-render pass through all mounted tab sections.

**After:** `OverviewTabPanel`, `TransactionsTabPanel`, `ReportsTabPanel`, and
`DataTabPanel` are wrapped in `React.memo`. All callback props are stabilised
with `useCallback`.

**Render impact:**
- Typing in the merchant filter updates `filterValues` → `TransactionsTabPanel`
  re-renders (expected). `OverviewTabPanel`, `ReportsTabPanel`, and `DataTabPanel`
  do **not** re-render (memo short-circuits because their props are unchanged).
- Switching from Transactions to Reports tab: `ReportsTabPanel` re-renders
  (section now visible); `TransactionsTabPanel` does not re-render.
- Estimated render reduction: ~60–75% fewer re-renders on inactive tabs
  during typical filter interaction sessions.

## Tab Switch Timing Baseline (Estimated)

| Transition | Estimated wall-clock (API + render) |
|---|---|
| overview → transactions | ~200 ms (single /transactions call) |
| transactions → reports | ~525 ms (parallel reports calls) |
| reports → data | ~165 ms (single /settings call) |
| data → overview | 0 ms (already mounted, no new calls) |

Note: these are estimates pending live tab-switch instrumentation via
`performance.mark`/`performance.measure`. Run `profile_tab_transitions.py`
for the API-latency component.
