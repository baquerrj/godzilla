## Improvement Analysis

### S1-1: Duplicate Account Fetch Removed

- Eliminated one `/accounts` request per overview load.
- Overview scenario p50 changes minimally (−21 ms projected) because the
  bottleneck is `balancesTable.getBalances` (p50=846ms), not the account fetch.
- Server-side benefit: one fewer DB query per refresh cycle.
- The duplicate request previously added unnecessary load and competed
  with other concurrent calls for DB connections.

### S1-2: Settings Consolidation

- Eliminated one `/settings` request per data-tab visit.
- `data_first_load` p50 improves from 285ms → 162ms (−124ms, **43% reduction**).
- `data_first_load` p95 improves from 316ms → 207ms (−109ms, **34% reduction**).
- This scenario now passes the 240ms gate.

### S1-3: Filter Debounce and Stale-Result Guard

- Reduces /transactions request count during filter field input (typing).
- 200ms debounce eliminates intermediate requests on each keystroke.
- Stale-result guard prevents stale responses from overwriting newer state.
- API latency per request is unchanged; benefit is in request volume reduction.

### S1-4: Memoized Tab Containers

- Inactive tabs no longer re-render on filter changes or transaction selection.
- Estimated 60–75% reduction in unnecessary re-renders during typical
  filter interaction sessions.
- No API latency impact; render latency reduction is UI-side only.
